Cross-cutting screens — auth, shell chrome and account

The surfaces every role touches and no surface owns: signing in, picking a role, resetting a password, the whole shell (rail, top bar, status bar and its three popovers), global search, account settings, and the states that replace a whole content region. Values are swept against 00-foundations/; nothing here is a new decision. The one thing genuinely derived is section G’s rail-destination list, taken from SOLUTION_DESIGN.md §2 cross-checked against each role’s own §7.5.* tool catalog.

A · Signing in

One shared sign-in for all six roles; the role decides the landing surface, never a separate login page. Email and phone share one field because drivers know their number and office staff know their email. Errors never disclose whether an account exists. No “Remember me”, no SSO, no “Sign up” — accounts are invite-only.

B · Password reset

Two screens sharing one card chassis. Screen A is reached from sign-in; screen B is a cold entry from an emailed link, with no session and no context. Neither screen ever confirms that an account exists, and the “sent” state is informational blue, not success green — nothing has succeeded yet.

Email only, not the combined "Email or phone" field sign-in uses. Same field height, padding and button as the sign-in card otherwise, because a drifting chassis reads as a different product mid-flow. prompt 3 artboard A · components.md §12

C · Top bar, help and the two popovers

56px top bar: facility switcher left, global search centre, then notifications, help and the user menu on the right. Both popovers are tier-3 Floating, opaque, 8px below the bar, non-modal — no scrim, nothing behind them is dimmed or blocked, Escape closes and returns focus to the trigger. The icon rail and status bar are out of frame in this section — they are drawn in section G, added 2026-08-26, together with the facility switcher’s open state. The rail’s destinations are role-scoped and are now derived there from SOLUTION_DESIGN.md §2 and the §7.5.* tool catalogs rather than invented.

Top bar — anatomy at rest

The facility switcher always shows the facility name, never an icon alone, and carries the only swatch of facility accent permitted outside the rail stripe. Search is a click target and a Cmd/Ctrl+K target for the same palette. components.md §7 · color.md §Facility accent (U59) · iconography.md

The unread count is spoken in the bell’s accessible name (“Notifications, 3 unread”), so the badge is never the only carrier of that fact.

F · States that replace the whole content region

Distinct from inline empty states because they replace the content region rather than a component inside it. The shell itself — rail, top bar, status bar — never unmounts; only this region changes. Every one names a cause and a next action.

Out of scope

Reached by a stale bookmark, a shared link or a revoked assignment. Never a bare 403, and never a confirmation that the resource exists. auth-and-scoping.md §Scope failures

Naming the facilities the user does have is safe; naming the one they hit is not. Repeated scope failures are logged — they are a signal worth having.

Deliberately the same message whether the shipment genuinely doesn’t exist or exists outside the viewer’s scope. Conflating the two is the correct behaviour here, not vagueness. components.md §13 (U72) · iconography.md

Two different causes, one string — because a distinguishing 404 is an account- and record-enumeration tool.

Error boundary — scoped, never whole-app

The queue, the dock board and the co-pilot each have their own boundary. A planner mid-decision must not lose the queue because the board threw. components.md §13 (U72)

“Report this” attaches the region name and a trace id — never a stack trace shown to the person using it. Safer action first in source order, so a fast keyboard user reaches Report before Try again.

Maintenance

Not hypothetical — the planned live-database migration is exactly the event this page announces. It always states an estimated duration, because a maintenance page that doesn’t reads as indefinite. components.md §13 (U72)

Icon rail — at rest, and expanded as an overlay

56px fixed, 4px facility stripe on the outer edge, active item marked by a 2px inner accent bar and never a background fill. Planner — one destination, facility-scoped. The stripe is Jaipur DC’s violet.

Carrier — one destination, hovered. No stripe: carriers are scoped by carrier_id, not by facility, so there is no facility to colour.

Carrier, expanded. 240px, tier-3 Floating, sitting on top of the content — the bars behind it have not moved.

One destination per role — because a rail destination is a surface, and this product has one surface per role (criterion in components.md §7). Ops → Exceptions (flag). Planner → Dock Command (chart-gantt; Queue and Board are tabs). Gate → Yard (warehouse; the two device contexts switch on a segmented control, per §12). Carrier → Fleet (package; shipments, exceptions and the on-time tile are sections of one dashboard). Admin → Admin (sliders-horizontal; Users, Rules, Policy and Audit are four tabs). The driver has no rail at all — the PWA runs 320–768px and carries its own chrome. Settings is reached from the user menu, not the rail, so it is not a destination either.

Corrected 2026-08-26. Carrier first had three destinations here, derived by counting SOLUTION_DESIGN.md §2’s jobs and §7.5.6’s tools — which contradicted 05-carrier-portal/screens.md, where that surface was already designed as “one sectioned dashboard … no tabs.” A job in §2 is not a destination, and neither is a tool in §7.5.*: the tool-catalog cross-check proves a job has backing, not that it has its own screen. The surface’s own screens.md is authoritative for navigation shape.

All five internal roles therefore have a single-destination rail — owner-confirmed, not an oversight. Facility switcher — open

A combobox, search-filterable, always showing the facility name and never an icon alone. The swatch here and the rail stripe are the only two places facility accent is permitted to appear. components.md §7 (U40) · color.md §Facility accent (U59) · auth-and-scoping.md

Changing facility clears row focus and any pending selection, so a stale selection can never be acted on in a new context. “All facilities” renders only for the cross-facility ops roles (§7.5.5 takes facility_id?, omitted = every facility in scope) and carries a dashed outline rather than a colour, because it is not a facility and must not borrow a facility’s hue. For the carrier role this whole control is absent from the DOM, not disabled — scope-denied is Hidden (U83).

Thirty-two artboards, one design system, six roles. What this board is testing: can a driver, a planner, a gate officer, a carrier manager and an admin all pass through the same door without any of them meeting a screen built for someone else? Three rules do most of the work here — an error never says which half of a credential was wrong, an operational time never appears without its dock and its date, and a control that is out of scope is absent rather than greyed. Tokens trace to 00-foundations/; screen contents to 00-foundations/stitch-prompts-shared-shell.md. Six items are flagged inline as gaps or placeholders rather than quietly invented.

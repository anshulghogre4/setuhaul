Prompt 7 · Reason-specific Reason section — NOTIFICATION_FAILED vs NOTIFICATION_UNROUTABLE

Prompt 12 · Co-pilot active — three fixed capabilities, and the two-gate draft

Three actions only; this is not a general chat feature, and there is no free-text input, no message history, no regenerate, no thumbs up/down, no model name or token readout, no streaming animation. The two-gate rule the design must not shortcut (U90, flows-and-states.md Flow 3): Approve moves the exact text into the thread composer, editable and unsent — it does not send. Sending is the ordinary composer Send in the detail pane, so the coordinator reads the same string twice. There is no "Approve and send" combined action, and it must not be invented — the last card shows the approved text sitting in the composer with [ Send ] still unpressed. Per-action loading puts a spinner in place of the leading icon, label unchanged, width frozen: loading never removes an action's own label and never reflows the pane. Summarise and Fetch context render inline and non-editable — they are context, not messages; they never enter the transcript and never get a Send action. Only a drafted reply can cross into the composer. Discard leaves nothing behind — no trace in the thread, no text in the composer, no confirmation prompt, because nothing was ever shown to the driver.

Prompt 14 · Capacity incident — collapsed, expanded, handed off, and scope-denied

One row per incident, always, regardless of how many shipments it affects — that rule is the component's whole reason for existing (components.md §17, Flow 4), and the affected count is part of the row's primary text, not a badge easy to miss. Each affected shipment carries its 3px neutral priority marker alongside the written priority word — the bar alone is never sufficient signal, and priority is a value ramp, never a hue, because red in this product means danger only. Every shipment row is strictly Read-only: no hover, no focus ring, no accent, no cursor change, and no per-shipment action of any kind — no confirm, reject, counter-offer or reschedule, even though the rows are queue-row-shaped. Acting happens only through the single button below. [ Request sequencer proposal ] is the only action ops has on an incident: it applies no capacity change, it asks the sequencer to compute one — a capacity incident is triaged in ops and applied in planner (U93). Prompt 15 · Reason picker — Cancel variant, over a flat scrim, with a toast above it

Resolve and Cancel are two different terminal states with two different meanings, not interchangeable "done" buttons — conflating them is the likeliest real mistake a coordinator makes under time pressure. Container is the smallest modal size, 480px, shadow-lg, over a flat scrim — dimming, never blurring (no glassmorphism anywhere in this product: text contrast must be verifiable, and it is not when the background depends on what is behind it). Escape dismisses, focus is trapped, restored to the trigger on close, and lands on the first interactive element, never on the committing button. A reason is required — a bare Cancel with no reason leaves no audit trail for why an SLA-tracked item closed. The internal-note label is always visible and the "(never shown to the driver)" qualifier is part of the label, not a tooltip. "What happens next" replaces the driver-message preview used in the planner's reject flow, because neither Resolve nor Cancel sends the driver anything; no driver-facing copy is invented for a message that is never sent. The dismiss button comes first in source order and sits ≥16px from the commit, so a keyboard user tabbing quickly reaches the dismissal first whatever the visual order. There is no "are you sure?" on top of this — the reason picker is the friction (U41). The toast on top demonstrates the stacking rule: toasts sit above modals, because a time-boxed undo that can be hidden is no undo.

Two things flagged rather than smuggled: the picker's container is never specified as modal, popover or inline (stitch-prompts.md Known gap 1) — the modal here rests on the reading that a reason picker is data collection, not a confirmation gate; and whether these two actions get the 5-second undo at all is unstated (Known gap 3), so the toast below shows the shared anatomy without asserting it fires for them.

Prompt 16 · Toast stack — bottom-left, max three, older collapsed

Bottom-left, 16px from both edges, maximum three stacked with 8px gaps; older ones collapse to a "+2 more" summary. The undo bar depletes linearly over exactly 5000 ms — linear because it represents literal elapsed time, not an eased transition (rendered here at ~62% remaining). The same 5-second window is also reachable by Cmd/Ctrl+Z regardless of where focus is: a toast a sighted user can click in five seconds is functionally unreachable for a screen-reader user who must first hear it announced and then navigate to it. Success is 4 s, dismissible, role="status", polite — a success does not need to interrupt. The error toast persists until dismissed, role="alert", assertive, with an explicit dismiss x; no error toast auto-dismisses. Toasts never carry the only copy of important information — a toast is a confirmation, not a record, so whatever it says is also true and visible somewhere in the console. No top-centre or top-right placement, no stack taller than three, no sound, no spinner inside a toast, and no toast for routine row arrivals (Prompt 3's count pill is that whole signal). Motion: 200 ms ease-out in, 120 ms ease-in out; under prefers-reduced-motion both become instant with the same time on screen.

Toast bodies for the success and error types are illustrative — Prompt 16 fixes their anatomy, timing, role and dismissal, not their wording. "Nothing has changed" in the error line is not illustrative: it is verbatim and mandatory.
